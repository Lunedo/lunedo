# Database

PostgreSQL 16 or newer is the only required datastore. Tables are defined with Drizzle in the module that owns them (`packages/server/src/<module>/schema.ts`) and collected in `packages/server/src/database/schema.ts`.

## Conventions

- Table and column names are snake_case. Drizzle maps the camelCase properties in TypeScript to snake_case (`casing: "snake_case"`), so schema files use camelCase keys without explicit names.
- Primary keys are UUIDv7, generated by the application with `primaryId()`. They sort by creation time, which keeps indexes compact. Tables that store the ID of an external system, such as the job queue, use that ID instead.
- Every table has `created_at` and `updated_at` from `timestamps()`: `timestamptz`, stored in UTC. `updated_at` is set by the application on every update.
- Foreign keys are always declared explicitly, with the `on delete` behavior spelled out.
- Every foreign key and every column used for lookups has an index. Unique rules are unique indexes, not application checks.
- Enumerations are PostgreSQL enums (`pgEnum`).
- Values encrypted with envelope encryption use the `encrypted()` column type (`bytea`) and are registered for key rotation; see [encryption.md](encryption.md).

## Migrations

Migrations are generated from the schema and are forward-only:

```sh
pnpm --filter @lunedo/server db:generate --name <short_description>
```

Review the generated SQL in `packages/server/drizzle/` before committing. Never edit a migration that is on `main`; write a new one instead.

Every process applies pending migrations at startup. A PostgreSQL advisory lock makes sure that only one node migrates when several start at the same time; the others wait and then find nothing left to do. Readiness (`/health/ready`) reports an error while the database schema is behind the code.

The job queue (pg-boss) manages its own tables in the `pgboss` schema.

## Tests

Integration tests run against a real PostgreSQL server. Set `LUNEDO_TEST_DATABASE_URL` to a database user that may create databases, for example the development database:

```sh
LUNEDO_TEST_DATABASE_URL=postgres://lunedo:lunedo@localhost:5432/lunedo pnpm test
```

Each test run creates a fresh, migrated database and drops it afterwards. Tests that need an empty database, or an instance state of their own such as setup, create their own; copies of the migrated template take a few milliseconds. `DROP DATABASE` waits for a checkpoint of the whole server, which takes seconds while other tests write, so inside a test run `drop()` returns once no connection is left and PostgreSQL removes the database in the background. The global setup of the server, API, collaboration and worker tests tags every database of the run with a run ID and drops what is still left when the run ends. Without the variable, database tests are skipped locally; in CI they are required.

End-to-end mail tests need Mailpit, which the development environment includes. Set `LUNEDO_TEST_MAILPIT_URL=http://localhost:8025`; its SMTP server is expected on port 1025 of the same host. Without the variable these tests are skipped locally; in CI they are required.
